# Build Mac: plan (2026-10-11)

Tracker row: ARC-15. The owner chose the approach on 11 October 2026.

## Goal

This Mac (an M1 Ultra with 20 cores and 128 GB) has run at a load average around 78 for days, with 61 worktrees on its external SSD. A second Mac, the owner's MacBook Pro with an M4 Max and 128 GB, takes the heavy runs the owner starts: the push gate and the whole suite on a commit, targeted tests, the regression suite's tiers, the release room's checks and the performance records. This Mac keeps its capacity for agents, video and rendering. When the build Mac can't be reached, the same command runs here, as it does today.

## Decisions

- **Over SSH, from the owner's own Terminal** (owner, 2026-10-11). Agents keep building here: the sandbox their shells run in refuses connections to the local network (a connection to the router failed with "Operation not permitted"), and relaying their jobs through a helper on this Mac would route around it. An agent that needs a heavy run gives the owner the line to run, as the release room already does for `mise run release`, and reads the results that come back into the checkout.
- **The release room's checks run on the build Mac; the cut stays here** (owner, 2026-10-11). This Mac's keychain keeps the Developer ID identity, the notary profile and the Sparkle key, and none of them goes to the build Mac. The dry run signs with the Developer ID identity, so it stays here too.
- **The build Mac's performance runs are its own series** (owner, 2026-10-11). Per-Mac lines on the performance page come first (ARC-09); then the README's card moves to the M4 Max, since this Mac is rarely quiet enough to record (a load average of 8 or below).
- **The build Mac sits plugged in with its lid closed** (owner, 2026-10-11). `pmset disablesleep`, the undocumented setting the tools for keeping a Mac awake closed rely on, keeps it awake with the lid closed whatever is connected. A virtual screen from BetterDisplay (owner, 2026-10-11), created once and connected at each login by `scripts/build-mac/virtual-screen.sh`, gives the tests that open windows, and the regression suite, a screen without a monitor or a dummy plug. It's set to a Retina mode that looks like 2560 × 1440, since this Mac's screens are Retina and the histogram's tests choose their references by the screen's scale; BetterDisplay's default is 1x at 5120 × 2880. Creating and connecting it are in BetterDisplay's free tier, which its README offers for non-business use. The parity step shows whether it stands in for a monitor.
- **The build Mac stays on macOS 27; only Xcode has to match** (owner, 2026-10-12). It runs macOS 27.0 and this Mac 26.6.2, with the same Xcode (26.6, 17F113), so both compile the same code against the same SDK. What runs the tests differs (the GPU driver, AppKit, the image decoders), and the parity step says whether its results stand for this Mac's.
- **Recipe goldens per GPU** (owner, 2026-10-12). The build Mac draws the lint chart byte for byte as this Mac does, but its renders of the bundled recipes differ from their goldens by a level in 2 to 12% of their pixels, and near black, where OKLab stretches the darkest levels, one level is more than RenderedRecipeTests' max: 8 of the 95 failed. The comparison stays as strict: each GPU keeps a set of golden renders recorded on it, the M1 Ultra's in each process version's folder and the M4 Max's in `apple-m4-max/` within it, and a new recipe, a recipe's new version or a new process version is recorded on the build Mac too ([look development](../recipes/look-development.md#shipping-a-recipe)).
- **The histogram's references per macOS version** (owner, 2026-10-12). On macOS 27, 106 of the histogram snapshot's 31,980 pixels differ from macOS 26's by more than the test allows, all of them in the readout's text. The references stay exact: macOS 26's where they were, and a later version's in a folder of its own (`Golden/macos-27`), recorded on a Mac running it.
- **Jobs run over plain SSH, with no job agent in the desktop session** (owner, 2026-10-12). Run in the build Mac's desktop session, the two suites that differ there (RenderedRecipeTests and HistogramGraphViewTests) failed exactly as over SSH, their figures identical to the digit, and the other reference suites pass over SSH, the ones that open windows among them. Whether the regression suite, which drives the app on screen, needs the desktop session is checked when `e2e` comes (step 6).
- **Agents reach it through a relay on this Mac's loopback** (owner, 2026-10-13), in place of the first decision's agents building here. `scripts/sandbox-relay.py`, installed once from the owner's Terminal, runs outside the sandbox as a LaunchAgent (or as a system LaunchDaemon, when macOS's Local Network privacy keeps a LaunchAgent off the local network; on this Mac a LaunchAgent reaches it), listens on 127.0.0.1:2223 and passes each connection on to the build Mac's SSH port. A block in `~/.ssh/config` sends `build-mac` to it only in a shell of the sandbox, so `ssh build-mac`, `git push` and `build-mac.py` work from an agent's shell unchanged, and the owner's Terminal goes straight to the build Mac. SSH stays encrypted to the build Mac and is checked against its known key. The owner left SSH port forwarding on for the build Mac's key (2026-10-13); agents are asked to use it for builds, tests and their results.
- **Agents build and test on the build Mac first, and here only when it doesn't answer** (owner, 2026-10-13), so this Mac keeps its capacity for agents, video and rendering. `build-mac.py test` runs `xcodebuild test` on an agent's working tree as it is, uncommitted and new files included; `mise run test`, `mise run gate` and `mise run e2e` go there first; and a Cursor hook (`.cursor/hooks/build-mac-first.py`) refuses `xcodebuild test`, the push gate and the regression suite run directly while the build Mac answers, naming the line that runs the same there. A run that records references stays here, since it writes them into the checkout, and so does building and running the app to look at it.
- **3 short tests and 2 long jobs at once; the regression suite and performance records alone** (owner, 2026-10-13). A test with `--only` takes one of 3 short lanes, so it never waits behind a suite; a gate or a scheme's whole suite takes one of 2 long lanes. The regression suite drives the screen and a performance record needs a quiet Mac, so each waits for the jobs running, and jobs that come meanwhile wait for it. A job whose lanes are taken waits in the build Mac's queue rather than running here, which at a load of 100 is still slower.
- **The build Mac's whole suite stands for this Mac's** (parity, 2026-10-13, settled by the owner). At origin/main, with the same Xcode, the build Mac ran 3,263 tests in 31 minutes, with the same results whether its lid was open or closed, so the virtual screen stands in for a monitor, and barely slower beside a second long job; this Mac ran 3,198 in 91 minutes at a load of about 100, its RedlampMaskingTests bundle having failed to load once (it passes rerun), and a check the sandbox skips runs only on the build Mac. Five tests failed only there. macOS 27.0.1, which installed itself overnight, draws the histogram's text differently from 27.0: its references were recorded again there, and the build Mac's security responses are turned off, so its macOS changes only when the owner updates it. CopySettingsTests leaves the editor window, whose frame is kept by name, at its smallest, and the build Mac's test runs keep that in their preferences where the sandbox keeps none, so EditorPanelsTests opened at 1,100 points: it now sizes its own window. And on macOS 27 a decode holds about one more copy of its samples (DecodeMemoryTests), Tab focuses none of the export dialog's fields, in the desktop session as over SSH (ExportSheetTests), and the library's previews come late while many tests run at once, leaving the loupe blank for a frame or fewer of them read ahead (LibraryNavigationTests, from time to time): each is a known issue on macOS 27, with a row of its own (ARC-19, UX-44, LIB-50).
- Considered and not chosen: a self-hosted GitHub Actions runner fed through a private repository, which agents could reach through the proxy (it can't be attached to the public repository, where a pull request from a fork could run its own code on it); and running agent chats on the build Mac itself, which splits orchestration across two Macs. The runner remains the way to let agents use the build Mac later.

## What exists

- `scripts/push-gate.py` checks a commit in a worktree of its own (`../darkroom-push-gate`, with its own DerivedData) at one of four levels (checks, reference, suite, full), and remembers a pass by the commit's tree in `build/push-gate/passed/<tree>`. A push whose tree passed at the level it needs goes straight through.
- `scripts/e2e.py` builds a test copy of the app, starts its executable and drives it in a home of its own; it needs an unlocked desktop session, and with `--focus` a Mac nobody is using. It writes `build/e2e/<commit>-<time>/report.json`, and `mise run release` accepts a passing, clean release-tier report with focus for the commit from the release copy's `build/e2e/`.
- `scripts/perf-record.sh` builds Release and appends a record to `docs/performance/history.jsonl`, marked noisy above a load average of 8. `scripts/perf-kit.sh` already measures another Mac as its own series, by AirDrop, and `scripts/perf-card.py` draws the card from the M1 Ultra's quiet records.
- The gitignored inputs a checkout needs: the sample raws (2.1 GB, which `mise run fixtures` and `mise run fixtures-shoots` download from raw.pixls.us), vendored LibRaw (`vendor/build`, `vendor/cache`) and the Swift packages (`Tuist/.build`, 220 MB). The gate's DerivedData is 3.2 GB.
- This Mac runs macOS 26.6.2 and Xcode 26.6 (17F113). CI's runner skips the GPU tests, so they have only run on this M1 Ultra; `ProcessStabilityTests` leaves room for another GPU's rounding, but no other GPU has been measured against it.

## Architecture

- **`scripts/build-mac.py`, on this Mac,** run from the owner's Terminal or an agent's shell:
  - `setup` runs `scripts/build-mac/setup.sh` there with this Mac's macOS and Xcode versions; `status` says whether the build Mac answers (SSH with a 12-second timeout, since the first lookup of its name can take 4 seconds and the relay allows 10), whether its macOS and Xcode match this Mac's, its load, free disk, lid setting and screens, which of this Mac's sample raws and models it lacks, and what it's running and has queued.
  - `gate [<commit>] [--suite | --full]`, `attach [<job>]` and `cancel [<job>]`; `release-checks`, on the commit of the checkout it's run from; `test --scheme <scheme> [--only <Target/Suite>]` and `e2e [-- <e2e arguments>]`, on the working tree, uncommitted and new files included, sent as a commit made with a temporary index that leaves the checkout's index and branch as they are; `models`, which copies this Mac's models where the build Mac lacks them (step 6); then `perf [<commit>]` (step 7). `mise run test`, `mise run gate` and `mise run e2e` run through it.
  - `release-checks`, which `mise run release-checks` runs in the release copy, is the regression suite's release tier with focus and then the push gate on every test suite, each skipped once it has passed on either Mac. The regression suite comes first: when the build Mac doesn't answer and it runs here, it takes this Mac's screen while the owner who started it is still at it.
  - The regression suite's test app is signed ad hoc there, without the hardened runtime: the build account holds no identities, and the hardened runtime's library validation refuses the app's own frameworks signed ad hoc ("different Team IDs", measured on 12 October). The black-box check of the signed app stays with the release, here.
  - It sends the commit with `git push` over SSH to the build Mac's clone, under `refs/build-mac/`, which the pre-push hook lets through; starts the job there; and prints its log as it grows. Ctrl-C cancels the job there; `--detach` leaves it running for `attach`.
  - It brings the results back: a gate's pass into `build/push-gate/passed/<tree>`, so pushing that commit (by the owner or an agent) goes straight through; the gate's test results, which the push gate keeps beside its log on either Mac and `scripts/test-results.py` compares; a regression report into `build/e2e/`, or the release copy's; a performance record appended to `history.jsonl`, to be committed; and each job's log, with the push gate's own, into `build/build-mac/<job>/`.
  - When the build Mac can't be reached, or its Xcode differs from this Mac's, it says so in one line and runs the same task here; a different macOS is reported and allowed. `--there` waits for the build Mac instead; `--here` doesn't try it.
- **Jobs over plain SSH.** The script sends a copy of itself with each command, which runs the build Mac's side: a job runs in the clone, at its commit, in a process of its own detached from the connection, so it carries on if the connection drops and `attach` picks its log up again. Jobs run under `caffeinate`, several at once, each in a lane of its size (decisions): a job takes the lane its checkout used last when it's free, and one whose lanes are taken waits, saying what for. The build Mac keeps a folder per job in `~/src/build-mac/jobs/`, with its state and log; a job whose process is gone without finishing (a restart) is reported as lost.
- **Lanes.** A clone at `~/src/build-mac/redlamp`, whose origin is GitHub and which this Mac pushes commits to; the push gate's worktree beside it (`redlamp-push-gate`), which a gate uses from a long lane; and a worktree for each test lane in `~/src/build-mac/lanes/` (`short-1` to `short-3`, `long-1` and `long-2`), each keeping its DerivedData between jobs so builds are incremental: a short test took 14 seconds cold and 4 warm. Each lane's inputs are cloned from the clone's with `cp -c`, as the gate does. The regression suite runs in the clone, alone.
- **An account for building,** an administrator (Homebrew's installer and the settings need one), logged in automatically, with no signing identities.

## Setting up the build Mac

`scripts/build-mac/setup.sh` does it, run in Terminal on the build Mac; its header has the line that downloads it, and `--help` says what it does. It installs Homebrew and the tools in `scripts/build-mac/Brewfile`, Xcode with its licence, first launch, Metal toolchain and an iOS simulator runtime (compiling the app's Icon Composer icon, `AppIcon.icon`, needs one even for the Mac app, and the workspace builds the Bench app's framework for iOS), PATH for commands run over SSH, the clone at `~/src/build-mac/redlamp`, mise's tools, the sample raws and the generated workspace, and sets the power, lid, virtual screen, screen lock, update, Remote Login and automatic login settings. Run again, it brings everything up to date. The owner, once:

1. macOS: the build Mac runs 27.0 and this Mac 26.6.2, which is allowed, since only Xcode has to match. On 11 October 2026 the App Store's Xcode is 27.0 and this Mac's is 26.6, so the script installs 26.6 (17F113) with `xcodes`, which asks for an Apple Account with access to Apple's developer downloads; when the App Store's version is this Mac's, it installs from the App Store with `mas`.
2. An administrator account for building, signed in to the App Store, then the script, with `--gate` to finish with a push gate on origin/main. Automatic login needs FileVault off; with it on, after each restart the build Mac serves again once someone logs in, and this Mac runs everything meanwhile.
3. Plugged in, with the lid closed; the virtual screen stands in for a display. Check that it is still awake and answers SSH an hour later.
4. On this Mac, an SSH key for that account and a `build-mac` host in `~/.ssh/config`, as the script prints when it ends.

## Risks

- Renders that differ between the two GPUs (step 5).
- A pass that covers less: tests skip on a Mac missing a sample raw or a model. `status` and the parity run compare the counts.
- Versions that drift: jobs run here until the build Mac's Xcode matches again. Its macOS already differs, which the parity step checks once and `status` reports each time. macOS 27.0.1 installed itself there on 13 October, with automatic macOS installs off, since security responses were still on, and changed the histogram's drawing; with them off, its macOS changes only when the owner updates it, and macOS 27's histogram references are recorded again after each update.
- A Python without `python3`: Homebrew provides the plain `python3` command only from its default Python, so the build Mac's first gate over SSH ran the scripts with macOS's 3.9 while the Brewfile named `python@3.14`. The Brewfile now names `python`, and the setup stops when `python3` is older than 3.11.
- Agents and the owner sharing it: with both long lanes taken, a third suite waits there, which can take longer than running here; `status` lists what's running and queued, and `--here` runs a check on this Mac. Through the relay an agent's ssh could ask the build Mac for port forwarding, which the owner left on (2026-10-13), so AGENTS.md asks agents to use it for builds, tests and their results only.
